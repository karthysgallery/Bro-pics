# Minimalist Cream/Gold/Brown Redesign — Design Spec

**Supersedes** the palette/tone from [2026-09-14-storefront-redesign-frames-only.md](2026-09-14-storefront-redesign-frames-only.md) (the Shopcart-style green redesign) — that session's *structural* work (Size/Frame Design/Orientation selectors, shared `ui/` primitives, `RecentlyViewedRail`, filter logic) stays; only the visual palette/tone changes here. Frontend-only (`apps/web`), no backend touched.

## What changed

- **Palette**: `pine` green replaced entirely with a warm cream/gold/coffee-brown palette (`tailwind.config.ts`): `gold` (`#C6A15B`), `gold-light`/`gold-dark`, `brown` (`#4A3220`), `brown-light`/`brown-dark`. `cream` lightened slightly (`#FBF7EF`). "Shiny" achieved via `bg-gradient-to-b` (light→dark) on buttons/icons plus soft shadows, not literal gloss.
- **Minimalist header**: the previous bold pine color-block header is gone — `Header.tsx` is now a light `bg-cream/95 backdrop-blur-sm` bar with a thin `border-gold/30` underline, brown text/icons, gold hover states.
- **Texture**: a subtle fixed noise overlay (`feTurbulence` SVG data-URI, ~3.5% opacity, `mix-blend-mode: multiply`) on `body::before` in `globals.css` — reads as warm/creamy paper rather than a flat fill.
- **Scrollbar**: hidden globally (`scrollbar-width: none` + `::-webkit-scrollbar{display:none}`) — scrolling itself is untouched, only the visual track/thumb.
- **Animation**: `components/motion/FadeIn.tsx` (hero, on-load) and `ScrollReveal.tsx` (homepage sections, on-scroll-into-view via `IntersectionObserver`). **Implemented as plain CSS transitions (opacity/translate-y class toggle), not `framer-motion`** — see "Lesson learned" below. `framer-motion` is still installed (`package.json`) as prep for the React Bits components the user will paste in next, since most of those depend on it; it's just not used by these two components.
- **Contrast fix**: the hero's dark overlay went from `bg-charcoal/20` to `/45`, plus a `text-shadow` on the heading/subtitle and a `border-cream/40` + stronger shadow on the gold CTA button — a flat low-opacity overlay let a gold-toned hero photo nearly swallow a gold button sitting on top of it. General rule going forward: never rely on a single accent color plus a light overlay for guaranteed contrast against a photo background — always pair with either a shadow/border or a strong-enough overlay.
- **Frames-only imagery**: every one of the 23 placeholder image slots (`public/placeholders/{categories,home,products}/*.svg`) now depicts an actual photo frame — no more mug/canvas/gift-box/heart/mood-board substitutes left over from the old multi-category catalog. Same technique as prior sessions (real photo embedded via `<image>` in an SVG wrapper at the existing file path, sourced from Wikimedia Commons' `Category:Empty picture frames` and related categories, visually verified via the Read tool before committing). The personalization-editor mockup PNGs stay untouched (functional geometry, not decorative — unchanged reasoning from prior sessions).

## Lesson learned: this session's Browser pane doesn't tick `requestAnimationFrame`

While verifying the hero's on-load animation, `framer-motion`'s `motion.div` applied its `initial` inline style (`opacity:0; transform:translateY(24px)`) on mount and then **never progressed** — confirmed via direct `requestAnimationFrame` test in the browser console (`rAF did NOT fire within 2s`). This was reproducible after a full clean server restart (`.next` cleared), ruling out HMR/stale-state causes. `setTimeout` fired fine in the same environment.

Switched both `FadeIn`/`ScrollReveal` to plain CSS transitions triggered by a class toggle (state set via `setTimeout(fn, 20)`, not `requestAnimationFrame`) — this works because CSS transitions are computed by the renderer based on elapsed wall-clock time since the property changed, not by an actively-ticking JS rAF loop. A `getComputedStyle()` read via `javascript_tool` can still report a stale/frozen mid-transition value in this environment even when the CSS transition is genuinely complete — **a screenshot (which forces a real paint) is the reliable verification method for anything CSS-transition-driven here, not `getComputedStyle`,** the opposite lesson from the mockup-mismatch issue noted in `PROJECT_STATUS.md`'s full-site QA pass entry (where screenshots were the unreliable one and DOM measurement was trustworthy) — both are true, for different kinds of checks: static layout measurement vs. time-based animation state.

**Implication for the upcoming React Bits components**: if any of them rely on `framer-motion`'s imperative `animate()`/spring physics (as opposed to plain `initial`/`whileInView` CSS-transition-backed props, which may behave differently), the same stuck-animation symptom could reproduce in this dev/preview environment. Verify with a screenshot after a real wait, not a `getComputedStyle` read; if it's still visibly stuck in a screenshot, suspect the same rAF issue and consider whether a CSS-only equivalent exists.
