# Personalization Engine — progress & hand-off

Living document. **Read this first in a new session.** Brief = the 50-point "generic template + state + mockup + print" spec the owner gave (template JSON = source of truth; PSD only a mockup asset; same template drives browser preview AND 300-DPI print; AI detection assists, admin verifies).

## Real-repo findings (Phase 1–2 inspection — DONE)
- A template system ALREADY exists: `FrameTemplate` (per variant, versioned, fractional `printableRects`, `textZones`, `clipartOptions`, single `maskUrl`, `overlayUrl`, `mockupUrl`). `Customization` docs are PER SLOT, pin `templateVersion`. Print worker = `services/print-render` (Sharp). Editor = plain HTML canvas (`EditorCanvas.tsx`, `PersonalizationEditor.tsx`, `PhotoCropModal.tsx`); no Konva.
- `docs/PRODUCTION_READINESS_AND_TEMPLATE_SPEC.md` and `docs/TEMPLATE_AUTODETECT_FEASIBILITY.md` (owner's earlier analysis) apply; the feasibility doc says: alpha-window detection is reliable, solid-gutter partial, textured/gradient needs manual; Dockerfile `node:20-slim` has no librsvg.
- **NOT in the repo (blockers for specific phases):** the "FOREVER AND ALWAYS" design asset (only unrelated text matches), ANY `.psd` files, any real table/wall mockup scenes. See "Needs from the owner".
- Design decision: v2 is a SUPERSET of the existing model with a lossless adapter, so every existing product keeps working. No second cart/order/product/storage system.

## DONE in session 2 (backend, no UI yet)
- **Template store + admin API (P11 backend):** `apps/web/lib/personalization-templates.ts` (Firestore `personalizationTemplates/{id}/versions/{n}`; createDraft/saveDraft/transitionStatus; published = immutable, edit = new draft version; publish runs `assertPublishable` + media-library asset-exists check). Routes: `/api/admin/personalization-templates` (list, create draft), `/[id]` (versions), `/[id]/versions/[v]` (get, PUT draft), `/[id]/versions/[v]/status` (publish needs `catalogue:publish`). Storefront read `/api/personalization-templates/[id]` (latest published, or exact published/archived version; NEVER drafts). Rules + 4 emulator rules tests (48 pass). Test util: `lib/fake-firestore.test-util.ts`.
- **Cart/order persistence (P8–10 backend):** `CartLine.personalization?` (templateId, templateVersion, state), `OrderItemSchema.personalization?` (frozen `OrderPersonalizationSnapshot`). `create-order` rebuilds every claimed personalization via `lib/personalization-order.ts` `buildLineSnapshot`: template must be PUBLISHED, each photo must be a ready upload owned by the caller, dimensions come from the upload record (can't spoof DPI), `checkCompleteness` re-run server-side; failure = 409 `personalization_invalid` before any order number/payment. Order fingerprint includes the design, so editing it and retrying makes a new order. Legacy lines untouched.
- **Print worker (P15 wiring):** `render-job.ts` renders items that carry a snapshot via `renderTemplate` from the FROZEN template+state (never the live template), loading photos via uploads and template art via `media/{id}.path`; legacy items keep the old path. Firestore deps implemented (`getOrderItemPersonalization`, `loadTemplateAsset`).
- **Mockups (P13/14 local):** `mockup-warp.ts` (homography, bilinear, AA edge, quad validation) + `local-mockup-renderer.ts` (`LocalMockupRenderer implements MockupRenderer`: base → warped artwork → foreground; cache key = scene + state fingerprint; unprepared scenes unsupported → reported, not faked). 89 tests in print-render.
- **Admin order view:** `components/admin/PersonalizationSummary.tsx` (template/version, slot→photo table, zoom/rotation, print-quality tier in words + dpi, "customer accepted" flag, texts); customer order page shows photo count + text.

## DONE in session 3 (lifestyle preview, client-side)
- `apps/web/lib/preview-scenes.ts`: config-driven scenes (Wall / Living room / Table, procedural CSS/SVG so they work with no photography) + `layoutFrameInScene` (frame drawn at its REAL proportion of the scene from variant inches; kept inside the scene max, oriented to the picture). `apps/web/lib/homography.ts`: rect→quad homography + CSS `matrix3d` for photographic scenes. `components/editor/LifestylePreview.tsx`: scene switcher, hang/stand shadows, glass sheen, photo-scene branch (design warped onto `artworkQuad`). Replaces the old hard-coded "View in Room" (fixed rectangle over product photo #2) in `PersonalizationEditor.tsx`; the legacy editor otherwise unchanged. Tests: `homography.test.ts`, `preview-scenes.test.ts`, `LifestylePreview.test.tsx`, flow test updated.
- **Realistic placement (session 3b):** `lib/frame-cutout.ts` cuts the editor composite (drawn on a paper-coloured square) out of its background by flood-filling from the image edges, so a window/mat inside the frame stays opaque; result is a transparent PNG cropped to the frame's outer edge (its real aspect). `LifestylePreview` now places that cut-out on a photo scene at its real size (`stageWidthIn`), casts a shadow away from the scene's `light`, nudges colour with `tone`, and has a `quad` (homography) mode for angled photos; a failed photo falls back to the drawn scene. Photo scenes are plain config: `{ backdrop:{type:'photo', src, aspect, credit}, frame:{x,y,anchor,maxFraction}, stageWidthIn, light, tone }`.
- **Real room photos (DONE, session 3c):** the four default scenes are real Unsplash photographs (free licence) in `apps/web/public/scenes/` with `CREDITS.md`: living room (Alexandra Gorn), bedroom (Clay Banks), wall (mk. s), table (NordWood Themes). Each is a 4:3 crop; `lib/preview-scenes.ts` holds the measured frame position, `stageWidthIn` (real-world width of the photo, estimated from a door/dresser/side table), light direction, tone and `minFraction`. A failed photo falls back to the drawn scene of the same `kind`. Found via the Unsplash connector (needed the owner to confirm their Unsplash email). To add or swap a scene: crop to 4:3 around the wall/table spot, add the file + credit, add an entry to `DEFAULT_PREVIEW_SCENES`, check it on screen at 12x18 and 16x20.
- NOT done: per-template/admin scene config UI (scenes come from `DEFAULT_PREVIEW_SCENES` or the `scenes` prop).

## DONE in session 4 (collage templates end to end)
- **Automatic collage detection (P12, classical — no LLM):** `packages/shared/src/personalization/slot-detection.ts` `detectPhotoSlots` finds photo areas in an uploaded design: transparent windows (design goes OVER photos) or, on a plain background, placeholder boxes / outlined boxes / sample photos (photos go OVER the design, grown 1 px so no sliver shows). Shapes: rect, rounded (radius estimated), ellipse, tilted (min-area rect), polygon; containers/outer borders ignored; clear notes when nothing usable is found. `templateDraftFromDetection` → draft template (a slot ≥2× any other becomes photo 1 "Main photo"). Server: `POST /api/admin/personalization-templates/detect` (`lib/collage-detection.ts`: sharp decode at 1200 px, `planCanvas` fits the design into the chosen variant's print size without stretching, warns about low design DPI).
- **Admin builder (P11):** `/admin/personalization-templates` (list + "New collage from image": name, media picker/upload, optional product size → detect → draft) and `/admin/personalization-templates/[id]` (live preview drawn by the shop renderer, drag/resize spaces, arrow-key nudge, inspector: name/required/shape/corners/tilt/hint/position, fill order, text fields with font/colour/size limits, print size & DPI, design over/under photos, background colour, validation panel, save/publish/new version/archive, "Try with your photos" local preview, "Use on products" per product or per size). Menu entry "Collage Templates". Pure edit helpers in `components/admin/template-builder/template-draft.ts`.
- **Product linking:** optional `personalizationTemplateId` on Product and Variant (variant overrides product; admin PATCH accepts it, `null` unlinks). Product page loads the latest PUBLISHED template per variant (`getPersonalizationTemplatesByVariant`); such variants get the new editor, all others keep the classic one.
- **Customer editor (P6/7):** `components/customizer/` — `render-template.ts` (canvas renderer matching the print renderer: layer order, crop/rotation matrix tested against `cropRectInOriginalPx`, shape masks, tilted slots, text sized with the print renderer's shared `estimateTextWidth`), `TemplateCanvas` (tap empty space → photo picker, drag to pan, pinch / Ctrl+scroll to zoom, arrow keys), `CustomizerPreview` ("Your design" / "In a room": design framed in a moulding of the chosen finish on the real scene photos at true size), `CustomizerControls` (bulk "Add photos" fills empty spaces in order, per-space tiles with quality dots, low-res confirmation, text with fonts/colours), `use-template-customizer` (undo/redo, local downscaled copy shown instantly, background uploads 3 at a time that wait out rate limits, drafts in localStorage for 14 days with ids only, export only when every image is loaded). Photos and artwork are served same-origin (`/api/uploads/[id]/image` with session/owner check, `/api/media/[id]/image` public media only) so the canvas can export.
- **Cart/checkout:** add to cart stores `{templateId, templateVersion, state}` + a thumbnail via `/api/uploads/preview`; editing from the cart reopens the line's size and design (`?edit=&variantId=`), moving to another size keeps the photos. Checkout now also refuses a design the variant doesn't offer and judges photo sharpness at the purchased frame size (`checkCompleteness(..., { printSizeIn })`, shared `canvasPrintWidthIn`). Upload rate limit raised to 30/min for collages. The print worker renders a template order at the purchased frame's 300-DPI size (`printScale` in `render-job.ts`, never below the template canvas), so a design drawn at 12×8 and sold at 18×12 still prints sharp.
- Verified in the browser with a generated 7-window design (detection in the page, uploads stubbed — no live Firebase writes): bulk add, drag/zoom, undo, room/table scenes at 12×8 and 18×12, low-res blocking + confirmation, add to cart, edit from cart, phone layout.
